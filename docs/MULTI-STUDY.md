# 여러 스터디 운영

GitHub 로그인 계정 하나로 여러 스터디를 운영하거나 초대받아 참여할 수 있습니다. 로그인만으로 다른 스터디의 데이터를 볼 수는 없습니다.

## 사용 방법

1. GitHub로 로그인하고 상단의 **내 스터디**를 엽니다.
2. **스터디 만들기**에서 이름, 소개, 정원을 입력합니다. 현재 정원은 1~20명, 한 계정이 운영할 수 있는 스터디는 최대 5개입니다.
3. **저장소 및 멤버 → 초대 링크 만들기**에서 링크를 발급합니다. 발급 후 7일간 유효하며 재발급은 해당 스터디의 이전 링크만 만료시킵니다.
4. 팀원은 링크를 열고 GitHub로 로그인합니다. 이미 로그인했다면 계정을 확인하고 **이 계정으로 참여하기**를 누릅니다.
5. 상단의 **스터디 전환** 또는 **내 스터디**에서 모임을 선택합니다. 선택은 기기에 저장되며 브라우저 탭의 요청은 그 탭에서 선택한 스터디에 고정됩니다.

각 스터디는 공통 문제형 또는 자율 목표형을 선택하고 문제 수와 마감 규칙을 설정합니다. 상세 내용은 아래 **스터디 운영 규칙**을 참고하세요.

## 데이터와 권한

- `members`는 GitHub 숫자 ID를 기준으로 한 전역 계정입니다. 기존 행과 외래키 이름을 보존하기 위해 이 이름을 유지합니다. 이 테이블의 이전 `role`, `slot`은 권한 판정에 사용하지 않습니다.
- `study_memberships`의 `(study_id, member_id)`가 소속과 역할을 정합니다. 운영 권한은 스터디마다 독립적입니다.
- `rounds.study_id`로 회차를 분리합니다. 회차 번호와 과거 기록 출처 키도 스터디 안에서만 고유합니다.
- 인증과 사진 검토와 풀이 공유는 해당 회차의 스터디에 속합니다. 원본 사진에도 `study_id`를 보관합니다.
- 모든 스터디 API는 `X-Puli-Study` 헤더의 멤버십을 서버에서 확인합니다. 헤더가 없으면 그 계정이 속한 기존 스터디 또는 첫 스터디만 사용합니다. 다른 스터디 ID를 지정하면 거절합니다.
- 저장소 연결은 개인 계정에 속합니다. 연결한 저장소를 한 번 조회하고 그 계정이 참여한 스터디들의 최신 공개 회차와 대조합니다. 비참여 스터디는 인증하지 않습니다. 코드와 메모를 다른 스터디에 자동 공유하지 않습니다.
- 문제 초안, 사진 및 OCR 상태, 풀이 초안, 운영자 초대 정보는 스터디 전환 때 분리와 초기화합니다. 다중 스터디 이전 전에 기본 스터디에 저장한 문제 초안은 같은 기기에서 계속 읽을 수 있습니다.

## 이전과 복구

`0008_multiple_studies.sql`은 임시 테이블에 원래 행을 복사한 뒤 외래키를 포함한 새 구조로 전환합니다. 기존 계정, 세션, 회차, 저장소, 인증, 사진, 공유 코드와 초대 토큰을 보존하고 `study`라는 첫 스터디에 기존 멤버를 연결합니다. 기존 정원은 5명이며 새 스터디만 생성 시 정원을 선택합니다.

운영 이전 전에 원격 D1 백업을 저장합니다. 운영 백업에는 비공개 데이터와 암호화된 인증 정보가 포함되므로 저장소에 넣지 않습니다. 복사본에 이전 SQL을 적용해 원래 열의 값과 사진 바이트를 비교하고 `PRAGMA foreign_key_check`를 확인합니다.

여러 스터디가 생긴 뒤 예전 단일 스터디 Worker로 단순 롤백하면 데이터 접근 범위가 맞지 않습니다. 복구 시에는 접근을 제한한 상태에서 호환되는 Worker와 DB를 함께 검토하며, 이전 후 새 데이터가 있다면 이를 별도로 보존해야 합니다. 자동으로 운영 데이터를 삭제하거나 이전 백업으로 덮어쓰지 않습니다.

## 검증

`tests/studies.test.js`는 이전 전 실제 형태의 세션, 사진, 인증과 공유 코드와 초대 데이터를 만들고 이전 후 값을 비교합니다. 계정만 등록된 사람의 기존 스터디 접근 거절, 독립 회차 번호, 스터디 간 사진, 풀이, 수정과 검토 차단, 기존 계정의 OAuth 초대 참여, 마지막 정원의 동시 가입과 저장소 조회 중복 방지를 검증합니다.

로컬 브라우저 검증은 별도 D1과 가상 GitHub 계정으로만 수행합니다. 운영 사이트에 가짜 팀원, 스터디와 인증을 만들지 않습니다.

## 스터디 운영 규칙

새 스터디 생성 시 또는 **저장소 및 멤버 → 운영 규칙 설정**에서 다음 항목을 설정합니다.

- 공통 문제형: 회차당 문제 수 1~30개, LeetCode 수와 나머지 프로그래머스 수
- 자율 목표형: 기간당 개인 목표 1~30문제, 인정할 플랫폼(둘 다 / LeetCode / 프로그래머스)
- 마감: 정해진 요일 또는 기간마다 날짜 지정, 기본 시각(한국 시간)

설정은 새로 등록하는 회차와 목표 기간부터 적용됩니다. 각 회차는 등록 당시 규칙과 실제 마감 시각을 보관합니다. 기존 회차는 문제 수와 운영 방식을 바꾸지 않으며 제목과 마감을 기존 수정 기능으로 수정할 수 있습니다. 다른 창에서 기본 규칙을 변경했거나 같은 내용을 먼저 저장하면 충돌을 안내하고 재확인을 요구합니다.

정해진 요일 방식도 운영자가 **문제 등록 / 목표 기간 등록**에서 시작일과 마감일을 확인해 공개합니다. 주간 회차를 자동 생성하는 스케줄러는 포함하지 않습니다. 기본 마감 시각이 이미 지났다면 다음 주의 마감을 제안합니다. 표시한 마감 분의 끝까지 인정하며, 예를 들어 20:30은 20:30:59.999까지입니다.

초기 설정은 공통 5문제(LeetCode 1 + 프로그래머스 4), 화요일 23:59입니다. 운영자는 스터디에 맞게 바꿀 수 있습니다. 마이그레이션 0009는 기존 열의 값을 변경하지 않고 기본 규칙과 마감 시각 열과 자율 문제 테이블을 추가합니다.

### 자율 목표 인증

자율 목표 기간은 공통 문제 목록 없이 등록합니다. GitHub에서는 연결한 저장소의 새 소스 변경과 해당 커밋 README의 정확한 문제 링크와 폴더를 확인하고 문제를 발견합니다. 다른 작성자, 문서만 변경한 커밋, 병합 커밋, 기간 밖 풀이, 허용하지 않은 플랫폼과 다른 문제 링크는 제외합니다. 기존에 완료한 스캔은 이어가고 새 기간이나 변경된 회차만 필요한 시점부터 다시 확인합니다.

사진 인증은 **문제 인증하기**에서 플랫폼, 제목과 문제 링크를 먼저 등록한 뒤 기존 OCR와 팀원 검토 흐름으로 제출합니다. 문제 등록만으로 인증되지 않습니다. 같은 문제를 GitHub와 사진으로 여러 번 제출해도 개인별과 기간별로 한 문제입니다. 확인 대기 사진은 목표에 포함되지 않으며 지각 사진은 기록을 보관하되 목표 달성 수에서 제외합니다.

공통 문제형은 지정된 문제별 표를 사용하고, 자율 목표형은 팀원별 진행률과 인증한 문제 목록을 표시합니다. 풀이 공유는 두 방식 모두 인증한 작성자의 동의를 받아 해당 스터디에서만 제공합니다.
